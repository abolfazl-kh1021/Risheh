## ۱. خلاصه تغییرات انجام‌شده

### چیزهایی که تغییر کرد

| فایل | تغییر |
| --- | --- |
| `prisma/schema.prisma` | `provider` از `sqlite` به `postgresql` + افزودن `directUrl` برای مهاجرت‌های CLI. همه مدل‌ها، فیلدها و ایندکس‌ها **بدون تغییر** ماندند |
| `prisma/migrations/2026…postgres_init/` | مهاجرت اولیه SQL تولیدشده — روی هر دیتابیس PostgreSQL تازه قابل اجراست (`prisma migrate deploy`) |
| `src/lib/db.ts` | کلاینت Prisma سطح تولید: singleton مقاوم، retry خودکار خطاهای گذرا، هِلپر تراکنش `dbTx`، لاگ query فقط در محیط dev (ازدست‌رفتن کارایی در prod برطرف شد) |
| `scripts/migrate-sqlite-to-postgres.ts` | اسکریپت مهاجرت داده یک‌باره: SQLite → PostgreSQL با تبدیل نوع‌ها، ترتیب صحیح کلید خارجی، تراکنش اتمی و صحت‌سنجی خودکار |
| `src/lib/actions/public.ts` | استعلام هولوگرام: افزودن `mode: "insensitive"` تا رفتار جستجوی غیرحساس به حروف SQLite حفظ شود (در PostgreSQL جستجوی `LIKE` حساس به حروف است) |
| `src/lib/actions/discounts.ts` | تراکنش بازنشانی کد تخفیف با retry پوشش داده شد |
| `package.json` | اسکریپت‌های جدید: `postinstall`، `vercel-build`، `db:migrate:deploy`، `db:migrate:sqlite2pg`، `db:studio` |
| `.env.example` | الگوی دو رشته اتصال Neon (pooled + direct) با پارامترهای پیشنهادی |
| `Dockerfile` + `docker-compose*.yml` + `docker/entrypoint.sh` | مسیر self-host به PostgreSQL منتقل شد (سرویس `postgres:16`، اجرای `migrate deploy` و seed هنگام بوت) |
| `.github/workflows/ci.yml` | CI به‌جای SQLite از سرویس PostgreSQL 16 استفاده می‌کند |
| `README.md` | به‌روزرسانی پشته فناوری |

### چیزهایی که تغییر نکرد (طبق درخواست)

- **هیچ فایل طراحی، کامپوننت UI، رنگ، فونت یا صفحه‌ای دست نخورده است.** همه تغییرات در لایه داده سمت سرور است.
- نام مدل‌ها، فیلدها، DTOها و رفتار اپلیکیشن عیناً حفظ شده — هیچ import یا API داخلی عوض نشده (خروجی `db` همان نام و همان API قبلی است).

### نکته مهم درباره جداول تخفیف

فایل SQLite قدیمی، ۴ جدول سامانه تخفیف (`discount_campaigns`، `discount_codes`، `discount_redemptions`، `discount_artworks`) را نداشت — یعنی این قابلیت پس از افزودن به اسکیما، هرگز روی SQLite اعمال نشده بود. در PostgreSQL این جداول حالا **وجود دارند** (خالی شروع می‌شوند) و کمپین تخفیف از پنل مدیریت کار خواهد کرد؛ قبلاً این بخش روی SQLite خطای «جدول وجود ندارد» می‌داد.

## ۲. ساخت دیتابیس در Neon

1. به [neon.tech](https://neon.tech) بروید و با GitHub ثبت‌نام/ورود کنید.
2. **Create project** را بزنید؛ نام پروژه مثلاً `risheh`.
3. Postgres version: **16** (یا بالاتر)، Region: نزدیک‌ترین به کاربران ایران — `eu-central-1` (فرانکفورت) انتخاب خوبی است.
4. پس از ساخت، از داشبورد **Connection Details** دو رشته را بردارید:
   - **Pooled connection** — دکمه گزینهٔ *Pooled connection* را فعال کنید. میزبان به `-pooler` ختم می‌شود. این برای **DATABASE_URL** است.
   - **Direct connection** — همان رشته بدون `-pooler`. این برای **DIRECT_DATABASE_URL** است.
5. رمز عبور را در جایی امن ذخیره کنید (فقط یک‌بار نمایش داده می‌شود).

> **چرا دو رشته؟** Neon روی اتصال pooled از PgBouncer استفاده می‌کند که برای هزاران اتصال هم‌زمانِ توابع serverless طراحی شده، اما عملیات DDL (مهاجرت اسکیما) باید از مسیر مستقیم و بدون pooling انجام شود. Prisma این دو مسیر را با `url` و `directUrl` از هم جدا می‌کند.

## ۳. تنظیم فایل .env

فایل `.env.example` را به `.env` کپی کنید و مقدارها را جایگزین کنید:

```env
DATABASE_URL="postgresql://USER:PASSWORD@ep-xxxxx-pooler.REGION.aws.neon.tech/neondb?sslmode=require&pgbouncer=true&connection_limit=5&pool_timeout=20&connect_timeout=15"
DIRECT_DATABASE_URL="postgresql://USER:PASSWORD@ep-xxxxx.REGION.aws.neon.tech/neondb?sslmode=require"
AUTH_SECRET="<خروجی openssl rand -hex 32>"
```

### معنی پارامترها

| پارامتر | مقدار پیشنهادی | دلیل |
| --- | --- | --- |
| `sslmode=require` | همیشه | Neon اتصال رمزنگاری‌شده اجباری دارد |
| `pgbouncer=true` | فقط در DATABASE_URL | Prisma را با PgBouncer سازگار می‌کند (prepared statement را غیرفعال می‌کند تا با حالت transaction-mode تداخل نکند) |
| `connection_limit=5` | ۵ برای serverless | هر instance تابع Vercel حداکثر ۵ اتصال نگه می‌دارد؛ PgBouncer سمت Neon هزاران instance را چندگذر می‌کند |
| `pool_timeout=20` | ۲۰ ثانیه | اگر همه اتصال‌های استخر مشغول بودند، حداکثر ۲۰ ثانیه منتظر می‌ماند (به‌جای خطای فوری) |
| `connect_timeout=15` | ۱۵ ثانیه | «سرد شدن» محاسبه Neon (scale-to-zero) گاهی بیش از پیش‌فرض ۵ ثانیه طول می‌کشد؛ این پارامتر خطای P1001 در اولین درخواست را حذف می‌کند |

> اگر اپ را با `next dev` یا `docker compose` محلی اجرا می‌کنید، همین مقادیر کار می‌کنند؛ برای اتصال به Postgres لوکال فقط host و رمز را عوض کنید و `pgbouncer=true` را حذف کنید (مضر نیست ولی لازم نیست).

## ۴. مهاجرت یک‌باره اسکیما و داده‌ها

### ۴-۱. اعمال اسکیما روی Neon

با `.env` تنظیم‌شده، از ریشه پروژه:

```bash
npm install            # postinstall خودش prisma generate را اجرا می‌کند
npm run db:migrate:deploy   # مهاجرت postgres_init را روی Neon اعمال می‌کند
```

این دستور همه ۲۵ جدول، ایندکس‌ها و کلیدهای خارجی را می‌سازد.

### ۴-۲. انتقال داده‌های SQLite

```bash
npm run db:migrate:sqlite2pg
```

اسکریپت به‌ترتیب این کارها را انجام می‌دهد:

1. خواندن ۲۱ جدول از `db/custom.db` (فقط‌خواندنی).
2. تبدیل نوع‌ها: تاریخ‌های epoch-millis → `timestamp`، بولین‌های 0/1 → `boolean`.
3. داخل **یک تراکنش اتمی**: پاک‌سازی امن (فرزند قبل از والد — اجرای مجدد بی‌خطر است) و درج همه ردیف‌ها با حفظ شناسه‌ها (cuid).
4. اجرای `ANALYZE` برای به‌روزرسانی آمار برنامه‌ریز کوئری (اولین کوئری‌ها سریع‌تر می‌شوند).
5. صحت‌سنجی: شمارش همه جداول بین SQLite و PostgreSQL مقایسه می‌شود؛ هر مغایرت = خروج با کد خطا.

نمونه خروجی موفق:

```
  ── verification (SQLite → PostgreSQL) ───────────
  ✓ users                  sqlite=    8  postgres=    8
  ✓ artworks               sqlite=   58  postgres=   58
  ✓ verification_events    sqlite=   54  postgres=   54
  ...
  ✅ Migration verified — every table matches row-for-row.
```

**پیش‌نمایش بدون نوشتن داده:** `DRY_RUN=1 npm run db:migrate:sqlite2pg`

> فایل `db/custom.db` را تا زمانی که اپ را روی Neon تأیید نکرده‌اید نگه دارید — این نسخه پشتیبان اصلی شماست. پس از تأیید می‌توانید آن را حذف کنید.

## ۵. استقرار روی Vercel

### ۵-۱. متصل کردن مخزن

1. پروژه را به GitHub push کنید.
2. در [vercel.com](https://vercel.com) → **Add New → Project** → مخزن را انتخاب کنید.
3. Vercel به‌طور خودکار Next.js را تشخیص می‌دهد.

### ۵-۲. متغیرهای محیطی

در **Project → Settings → Environment Variables** همه را برای Production (و Preview) ثبت کنید:

| نام | مقدار |
| --- | --- |
| `DATABASE_URL` | رشته pooled Neon (با `-pooler` و پارامترهای بخش ۳) |
| `DIRECT_DATABASE_URL` | رشته direct Neon (بدون `-pooler`) |
| `AUTH_SECRET` | خروجی `openssl rand -hex 32` |

### ۵-۳. دستور Build

اسکریپت `vercel-build` در `package.json` همین کار را می‌کند؛ Vercel اگر آن را نیافت، همان Build Command پیش‌فرض را با این مقدار جایگزین کنید:

```
prisma generate && prisma migrate deploy && next build
```

با این کار هر دیپلوی، پیش از build، مهاجرت‌های در انتظار را روی Neon اعمال می‌کند.

### ۵-۴. نکات Runtime

- همه Server Actions و صفحات روی **Node.js runtime** اجرا می‌شوند (پیش‌فرض Next.js) — Prisma با Edge runtime سازگار نیست و نیازی به آن هم نیست.
- بعد از دیپلوی، یک‌بار `https://<your-app>.vercel.app` را باز کنید؛ اولین درخواست ممکن است به‌خاطر سرد شدن Neon چند صد میلی‌ثانیه کندتر باشد — طبیعی است.

## ۶. معماری کارایی (سرعت) دیتابیس

لایه‌های سرعتی که اکنون فعال هستند:

### ۶-۱. سطح اتصال
- **استخر اتصال PgBouncer Neon** با endpoint پول‌شده: هزاران درخواست هم‌زمان توابع serverless بدون به‌پاشیدن اتصال واقعی به Postgres.
- **Singleton کلاینت** در `src/lib/db.ts`: هر instance تابع فقط یک PrismaClient می‌سازد؛ در dev هم با `globalThis` از نشت اتصال هنگام hot-reload جلوگیری می‌شود.
- `connection_limit=5` + `pool_timeout=20`: تعادل میان سرعت پاسخ و مصرف اتصال Neon (پلن رایگان: محدودیت اتصال هم‌زمان).

### ۶-۲. سطح کوئری
- **کش TTL کاتالوگ عمومی** (`src/lib/cache.ts`): کاتالوگ (دسته‌ها + آثار منتشرشده + وبلاگ) ۱۰ ثانیه کش می‌شود با محافظت stampede (درخواست‌های هم‌زمان یک loader مشترک دارند) و ابطال صریح پس از هر نوشتنِ مؤثر بر کاتالوگ. روی Neon، هر بازدید عمومی گرم از کش پاسخ می‌گیرد نه از شبکه.
- **کوئری‌های موازی**: `loadAppData` همه خواندنی‌های هر نقش را با `Promise.all` هم‌زمان می‌زند (بدون آبشار).
- **تجمیع در دیتابیس**: درآمد ادمین با `aggregate` در Postgres محاسبه می‌شود، نه بارگذاری همه سفارش‌ها در حافظه.
- **ایندکس‌ها**: ۲۲ ایندکس (تک‌ستونی و ترکیبی) در مهاجرت اولیه ساخته می‌شوند — همه `WHERE`/`ORDER BY` های مسیر داغ پوشش داده شده‌اند.
- **ANALYZE پس از مهاجرت**: برنامه‌ریز کوئری از اول با آمار درست تصمیم می‌گیرد.

### ۶-۳. سطح لاگ
- لاگ `query` که قبلاً در همه محیط‌ها روشن بود (سربار سریال‌سازی هر کوئری) حالا **فقط در dev** فعال است؛ در production فقط `warn` و `error` لاگ می‌شود.

### ۶-۴. تنظیمات توصیه‌شده بعدی (اختیاری)
- در پنل Neon، اندازه compute را بر اساس ترافیک بالا/پایین ببرید (Free: 0.25 CU کافی است).
- اگر بازدید جهانی دارید، **Neon Autopilot** یا Replicas را بررسی کنید؛ برای ایرانِ داخل، latency فرانکفورت حدود ۶۰–۹۰ms است که با کش TTL اپ عملاً پوشش داده می‌شود.

## ۷. جلوگیری از خطاها — سیستم Retry و مدیریت خطا

### ۷-۱. retry خودکار خطاهای گذرا (`src/lib/db.ts`)

اپلیکیشن این کلاس‌های خطا را **به‌طور خودکار با backoff نمایی + jitter** تا ۴ بار تلاش مجدد می‌کند:

| کد | معنی | سناریوی رایج |
| --- | --- | --- |
| `P1001` | دسترسی به سرور دیتابیس ممکن نشد | سرد شدن Neon، لرزش DNS |
| `P1002` | تایم‌اوت برقراری اتصال | سرد شدن طولانی پس از هفته بی‌استفاده |
| `P1008` | تایم‌اوت عملیات | کندی گذرا شبکه |
| `P2024` | تایم‌اوت گرفتن اتصال از استخر | اوج ترافیک لحظه‌ای |
| `P2034` | تداخل نوشتن در تراکنش (deadlock/serialization) | دو ادمین هم‌زمان روی یک رکورد |
| SQLSTATE `40001` / `40P01` | خطای پیش‌فرض PostgreSQL | همان موارد بالا در سطح دیتابیس |

**خطاهای منطقی هرگز retry نمی‌شوند** (`P2002` نقض یکتایی، `P2003` نقض کلید خارجی، `P2025` رکورد یافت نشد) — این‌ها فوری به فراخواننده برمی‌گردند تا رفتار اپ قابل پیش‌بینی بماند.

### ۷-۲. تراکنش اتمی امن (`dbTx`)

برای نوشتن‌های چندمرحله‌ای از `dbTx` استفاده کنید:

```ts
import { dbTx } from "@/lib/db";

await dbTx(async (tx) => {
  await tx.order.create({ data: { … } });
  await tx.artwork.update({ … });
});
```

— timeout و maxWait منطقی دارد و روی تداخل نوشتن هم retry می‌کند.

### ۷-۳. محافظت‌های دیگر (از قبل موجود + تازه‌ها)

- محاسبه جمع سفارش همیشه سمت سرور؛ مجوزدهی در Server Actions (اعتماد به کلاینت وجود ندارد).
- Rate limit سمت سرور برای فرم‌های عمومی (تماس، استعلام اصالت).
- اعتبارسنجی zod روی همه ورودی‌های اکشن‌ها.
- صحت‌سنجی اتصال در ابتدای اسکریپت مهاجرت + خروج non-zero در هر مغایرت.
- `dbHealthCheck()` آماده است اگر بخواهید `/api/health` را DB-aware کنید.

## ۸. عیب‌یابی — جدول خطاهای رایج

| خطا | علت | راه‌حل |
| --- | --- | --- |
| `P1001 Can't reach database server` | URL اشتباه، یا compute خاموش/سرد | صحت رشته‌ها؛ یک‌بار در پنل Neon «Restart compute»؛ `connect_timeout=15` را نگه دارید (retry خودکار هم فعال است) |
| `P2024 Timed fetching connection` | استرحاق اتصال — connection_limit زیاد در همه instance ها | `connection_limit` را به ۵ یا کمتر برانید؛ مطمئن شوید از endpoint `-pooler` استفاده می‌کنید |
| `prepared statement "s…" already exists` | استفاده از direct URL در runtime یا نبود `pgbouncer=true` | DATABASE_URL باید pooled + `pgbouncer=true` باشد |
| `P3006 / migration failed` در build | اجرای migrate روی endpoint pooled | فقط DIRECT_DATABASE_URL (بدون pooler) برای مهاجرت — همین الگو در `schema.prisma` اعمال شده |
| `the URL must start with the protocol postgresql://` | متغیر محیطی قدیمی `file:…` روی `.env` غلبه کرده | مقدار shell/سرویس را حذف یا اصلاح کنید؛ اسکریپت dev این حالت را خودکار نادیده می‌گیرد |
| خطای unique در ثبت‌نام/کد تخفیف (`P2002`) | تکراری بودن ایمیل/کد | رفتار درست است؛ پیام کاربر پسند سمت اپ موجود است |
| دیپلوی Vercel خطای build دیتابیس | نبودن متغیرهای محیطی در build | هر دو URL را در Vercel برای همه محیط‌ها ثبت کنید |
| اولین درخواست پس از نیم‌ساعت سکوت کند | سرد شدن Neon (scale-to-zero) | طبیعی است؛ در صورت نیاز compute را روی حالت «Always on» بگذارید (هزینه دارد) |

**گزارش زنده:** در Vercel → Logs، خطاهای Prisma با پیشوند `[db]` (تلاش مجدد) یا `prisma:error` دیده می‌شوند.

## ۹. سؤالات متداول

**داده‌های من الان کجاست؟**
همه ۲۱۹ رکورد SQLite (۸ کاربر، ۵۸ اثر، ۵۸ شناسنامه اصالت، ۵۴ رخداد آزمایشگاه، سفارش‌ها، وبلاگ، …) در Neon هستند و شناسه‌ها عیناً حفظ شده‌اند — پیوندها و کوکی‌های قدیمی نمی‌شکنند.

**اگر دوباره `db:migrate:sqlite2pg` را اجرا کنم چه می‌شود؟**
امن است: داخل تراکنش، جداول Postgres خالی و دوباره از SQLite پر می‌شوند. اما **مراقب باشید**: تغییرات ثبت‌شده در Postgres پس از آخرین اجرا (سفارش جدید، ثبت‌نام جدید…) از بین می‌روند. این اسکریپت یک‌بارمصرف است.

**SQLite را می‌توانم بعداً برگردانم؟**
اسکیمای Prisma ما PostgreSQL-محور شده؛ فایل `db/custom.db` دست‌نخورده به‌عنوان پشتیبان باقی است. برگشت یعنی بازگرداندن provider و بازسازی — توصیه نمی‌شود.

**پنل مدیریت تخفیف چرا قبلاً کار نمی‌کرد؟**
جداول تخفیف در SQLite هرگز ساخته نشده بودند؛ حالا در Postgres موجودند و از پنل ادمین قابل مدیریت‌اند.

**قابل اجرا با Docker هم هست؟**
بله — `docker compose up -d --build` سرویس `postgres:16` را با اپ بالا می‌آورد؛ entrypoint خودش مهاجرت و (در دیتابیس خالی) seed دمو را اجرا می‌کند.
